## Localization Test Suite

本测试计划用于规范客户端多语言（本地化）测试的策略和实施方案，重点覆盖 UI 文案、布局、输入输出、区域设置等多方面，测试框架建议统一使用 pytest。

---

### 1. 测试目标

- 确保应用在各支持语言下的 UI 文案完整、准确、无明显语言错误或乱码。
- 验证多语言切换行为正确，语言设定对整个应用生效且可持久化。
- 确保不同语言环境下的界面布局不破版、不截断、不重叠。
- 验证与区域设置相关的功能（时间、日期、数字、小数点、货币等）在不同语言/地区下表现正确。
- 保证在多语言环境下日志、文件路径、配置文件等无编码问题，避免因本地化导致的崩溃或功能异常。
- 为 CI/CD Pipeline 提供一套可重复、可扩展的多语言回归测试集，与其他功能/安装测试套件配合使用。

---

### 2. 测试范围

- 语言与区域
  - UI 语言：简体中文、英文为必测语言，可扩展到其他语言（如日文、德文等）。
  - 区域设置：与操作系统区域设置相关的行为，例如日期格式、时间格式、数字分组、小数分隔符等。
- UI 文案
  - 菜单、按钮、工具栏、对话框、提示信息、错误信息。
  - 启动界面、欢迎向导、设置面板、关于对话框等常见入口。
  - 系统托盘菜单、通知气泡以及系统级集成的文案（如文件关联右键菜单）。
- 布局与样式
  - 不同语言下的窗口尺寸、控件对齐、文本换行、文字截断/溢出。
  - 右侧/左侧对齐、图标与文字间距。
  - 高 DPI 缩放、多屏幕缩放比例下的多语言显示。
- 输入与输出
  - 多语言环境下接收不同编码的文件名、路径、项目名称（含中文、特殊符号、emoji 等）。
  - 日志文件、配置文件、导出报告中的本地化文案和编码。
- 与其他模块的集成
  - 与安装/卸载模块的配合：安装语言选择、卸载向导语言、安装后的默认语言。
  - 与网络模块的配合：服务端返回多语言信息（如果有）。

不在本计划范围内的内容（如业务功能正确性、性能测试）由其他测试套件覆盖，多语言套件只检查“在多语言环境下表现是否正确”。

---

### 3. 测试环境

- 操作系统语言和区域设置
  - Windows 10/11（x64）：
    - 系统显示语言：中文（简体）、英文（美国）为基础组合。
    - 区域设置：`zh-CN`、`en-US` 等。
  - 如后续需要支持其他平台，可扩展到 macOS / Linux。
- 应用语言设置
  - 应用内部的语言切换（设置界面中的语言选项）。
  - 通过配置文件或命令行参数指定启动语言（如果支持）。
- 字体与编码
  - 默认系统字体以及应用自带字体（如使用自定义 UI 库）。
  - UTF-8 编码为主，避免系统 ANSI 编码造成的混乱。
- 测试数据
  - 含中文、英文、数字、标点、特殊字符（如 `ß`、`é`）、emoji 等的测试文件名和项目名称。
  - 多语言字符串资源文件（如 `.json`、`.po`、`.resx` 等），作为校验基线。

环境准备尽量由 pytest fixture 统一管理，例如：

- `language_env`：负责设置/恢复应用语言和系统区域设置。
- `localized_test_data`：提供包含多语言字符的测试数据路径。
- `app_client`：统一应用的启动和关闭，支持传入语言参数。

### 4. 用例设计（pytest 视角）

#### 4.1 目录结构建议

```text
test_framework/
  localization_suite/
    conftest.py
    test_language_switching.py
    test_ui_strings.py
    test_layout_stability.py
    test_datetime_and_number_format.py
    test_file_and_path_encoding.py
```

所有本地化测试用例统一使用一个 pytest 标记，例如：

- `@pytest.mark.localization_suite`

便于在 CI 中按 Suite 维度运行整个多语言测试集。

#### 4.2 关键 fixture 设计

- `language_env(default_lang)`：
  - 作用：在用例运行前将应用语言切换到指定语言，用例结束后恢复原始语言。
  - 使用方式：
    - 通过参数化在同一用例上跑多种语言，例如 `["zh-CN", "en-US"]`。
- `app_client(language_env)`：
  - 启动应用时附带语言参数（如支持），或利用配置文件指定语言。
  - 提供基本操作能力（打开主界面、导航到设置等）。
- `localized_test_data`：
  - 提供不同语言/字符集的文件名、项目名称等，供功能用例使用。

#### 4.3 核心测试场景

1. 语言切换与持久化
   - 前提：应用支持中文和英文。
   - 步骤：
     - 启动应用，切换到英文，重启应用。
   - 断言：
     - 设置面板显示当前语言为英文。
     - 主要菜单、按钮、状态栏的文案显示为英文。
     - 再切换回中文，检查同样的持久化行为。

2. UI 文案完整性
   - 前提：提供多语言字符串资源表或截图基线。
   - 步骤：
     - 在不同语言下遍历主菜单、设置面板、关键对话框。
   - 断言：
     - 不存在明显未翻译文本（仍为英文或占位符）。
     - 不存在乱码或不支持的字符。

3. 布局稳定性
   - 重点场景：
     - 文案在英文时较短，在中文/德文时变长。
   - 断言：
     - 不出现文字被截断、控件重叠、按钮被挤出可视区等问题。
     - 高 DPI 缩放下布局仍然合理。

4. 日期和数字格式
   - 在 `en-US` 与 `zh-CN` 环境下分别验证：
     - 日期格式（如 `2025-01-24` vs `1/24/2025`）。
     - 时间格式（12/24 小时制）。
     - 数字格式（小数点与千位分隔符差异）。
   - 断言：
     - UI 上的日期、时间、数值显示符合当前语言和区域习惯。

5. 文件名和路径编码
   - 使用包含中文、空格和特殊字符的路径（例如 `D:\测试项目\多语言\项目_ß_测试`）。
   - 断言：
     - 应用可以正常打开、保存、导出到这些路径。
     - 日志中路径显示正常，无乱码或截断。

6. 错误提示与异常信息
   - 模拟常见错误（如网络错误、文件不存在、权限不足）。
   - 在不同语言下检查错误弹窗的标题和正文是否对应当前语言。

### 5. pytest 套件管理（单一 Suite）

多语言测试只作为一个整体套件管理，不再按 UI 文案/布局/编码分别拆分多个 Suite。

- 统一标记：
  - 所有本地化相关用例统一加上 `@pytest.mark.localization_suite`。
- 目录建议：
  - 在现有 `test_framework` 目录下单独建立 `localization_suite` 子目录。
  - 该目录中的所有用例都属于同一个 Suite，并统一使用 `@pytest.mark.localization_suite`。
- 运行示例：
  - 本地运行整个多语言套件：
    - `pytest test_framework -m localization_suite`
  - 在 CI（例如 Jenkins）中：
    - 测试命令使用 `-m localization_suite`，并结合 Allure 输出报告。

---

### 6. 报告与追踪

- 报告生成：
  - 使用 pytest + Allure 输出本地化测试报告。
  - 所有多语言用例输出到统一的 `allure-results` 目录。
- 用例设计规范：
  - 每个用例描述清楚测试语言、区域设置和前置条件。
  - 断言内容尽可能定位到具体控件或页面，便于问题复现。
- 缺陷追踪：
  - 本地化缺陷（L10N）建议加独立标签，如 `L10N-ZH`、`L10N-EN`。
  - 安装、多语言、功能套件之间共享缺陷编号，方便交叉分析。

---

### 7. 与其他测试套件的协同

- 与 Installation and Uninstallation Test Suite 的关系：
  - 安装过程中的语言选择、安装后的默认语言由安装套件覆盖。
  - 本地化套件重点关注“安装完成后的应用内多语言行为”。
- 与功能测试套件的关系：
  - 功能套件验证“功能是否正确”，在默认语言下为主。
  - 本地化套件在关键功能上做抽样，验证“在不同语言下功能表现是否一致且文案正确”。
